# 队友 B：图片加速器、DDR 与板端集成

## 你负责什么

依据 A 的整数计算规范，实现 GridDehazeNet 的 KV260 加速器及 Vivado 系统集成。此次只考核单张图片，不设视频 FPS 门槛，不因追求吞吐擅自降低图片分辨率。

## 立即开始的三件事

1. 阅读 [总说明](README.md) 和 [A 的任务](2.0.1_队友A_去雾模型定点与Golden.md)，和 A 确认图、算子语义及接口。
2. 提交可复用计算引擎、DDR scratch、片上缓存和数据搬运方案，先做资源与带宽估算。
3. 优先验证普通卷积和带目标尺寸的转置卷积，再接 dense block、多尺度融合和完整图。

## 现有工程边界

- 板卡：KV260 revB / K26；Ubuntu 22.04.4、内核 `5.15.0-1027-xilinx-zynqmp`。
- 已通过的是 `weather_fpga_integration` 的 signedfix 基线，来源提交 `e8662ce5bd177f4014da469ab9885eca06e396f3`。
- 基线 BIN SHA256：`3cc937d0b921c87ef3b2101309ae2fc3261c132dfd5f95c90539087a1fe86ebd`。
- 旧 weather IP 基址 `0xA0030000`、PL0 约 100 MHz；旧输入/输出经 HP0/HP3。这些是基线事实，不代表新模型可以直接沿用旧寄存器语义。
- 基线整个设计资源：LUT 63.22%、DSP 77.00%、BRAM 50%、URAM 73.44%。它包含其他现有 IP，不能把剩余资源视为全部可用预算。
- 请先确认新设计是否替换旧 weather IP、是否保留其他功能，并明确报告。不要自行删除共享时钟、复位或其他队友模块。
- 使用与你的 KV260 工程兼容的新版 Vivado/Vitis；用户本机没有这套新版工具。

## 推荐架构

采用按层/块复用的计算引擎，权重/中间特征按计划在 DDR 与片上缓存之间流动。不是将整个网络每层并行铺开。

- 模块覆盖：普通卷积、转置卷积、ReLU、拼接寻址、按通道加权及加法。
- 约 95.8 万参数与约 263 GMAC/720p 帧只是参考规模；必须报告实际设计资源和测得耗时。
- 720p、16 通道 INT16 特征约 29.5 MB，整帧特征不能全存片上。请提交每个特征的生存期、DDR 大小、复用/别名规则和峰值 scratch。
- 如做空间分块：必须分析完整图的感受野、下采样/上采样相位及 halo。不能沿用 TinyRestore 的 6 像素 halo。全图参考与分块结果要核对边界。
- 允许单张图耗时较长。先证明完整网络正确，再根据实测瓶颈优化。

## 与软件侧先对齐接口

以下是待共同冻结的接口项目，不是现成寄存器 ABI：

| 项目 | 必须明确的约定 |
|---|---|
| 版本 | 新模型 ID、寄存器 ABI 版本；不能让旧驱动误识别为旧 task=1 |
| 缓冲区 | input、output、weights、scratch 的物理地址、长度、对齐、可寻址范围 |
| 图像 | H/W、RGB/NCHW 布局、signed 数据类型及每段尺度 |
| 权重 | 加载一次复用还是每次请求加载；只读保护及版本匹配 |
| 控制 | START/DONE/IDLE、返回码、错误状态、非法参数的行为 |
| 超时 | 何时能证明无未完成 AXI 事务；完成未知时必须保留仍可能使用的 DMA 缓冲区 |
| 性能 | 核心耗时与包含传输/显示的请求耗时分别报告 |

现有驱动使用内核 coherent DMA 和明确的 ownership 锁。不要让用户态随意 /dev/mem 写地址来替代正式驱动。当前绕过 SMMU 的平台约束及 DMA 地址限制需要结合最终 DT/XSA 审核，不擅自修改全局 SMMU 或共享复位策略。

HP0/HP3 基线寄存器 `0xFD380000`、`0xFD380014`、`0xFD3B0000`、`0xFD3B0014` 板端读到均为 `0x000003B0`（低两位 0）。如沿用同一宽度配置，应与新 XSA 一致；不要把这组值当作无需检查即可写入的初始化脚本。

## 验证与交付

1. 算子仿真逐元素对齐 A 的整数 Golden，尤其是负数、舍入、累加溢出和奇数尺寸。
2. 完整网络仿真；若有分块，单独覆盖块边界和四周 padding。
3. 综合、实现：给出 LUT/FF/DSP/BRAM/URAM、时序、目标时钟、实际路由状态及工具版本。
4. 旧项目曾在 Vivado 优化 DSP 级联时改变符号/截断语义。阅读现有 signedfix 约束，保留可复现脚本；对最终实现做能覆盖该风险的数值验证，不能只凭 C 仿真或 OOC 综合通过宣布交付。
5. 提交 bit、XSA、BIN、HWH/地址表、设备树资源定义、完整寄存器说明、构建脚本、SHA256 manifest、整数测试输入输出及验证报告。
6. 留下可恢复的旧版本；上板由软件侧按新的 ABI 适配后操作。首张图片通过后再扩大样本，不重复进行无目的的小测试。
